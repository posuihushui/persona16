# 微信支付密钥轮换

接入手册见 [wechat-pay.md](./wechat-pay.md)。这份文档只讲密钥过期和轮换。

## 为什么这件事必须提前准备

微信用来给回调签名的公钥会更换。更换时微信不会等你，它会直接开始用新的密钥签名，回调头 `Wechatpay-Serial` 换成新的序列号。

如果你的配置里只有旧序列号，验签会失败，回调被拒绝。表现是：**用户付了钱，但权益没发放**。而且因为回调被拒，微信会不断重试，日志被刷屏，你却不知道是密钥的问题。

所以轮换的核心不是「换掉旧的」，是「新旧同时可用一段时间」。

## 三类材料，三种过期方式

| 材料 | 谁生成 | 会不会过期 | 换掉之后的影响 |
| --- | --- | --- | --- |
| 微信支付公钥 / 平台证书 | 微信 | 会。平台证书有效期 5 年，微信支付公钥由微信按需更换 | 验不了回调签名，权益发不出去 |
| 商户 API 证书 | 你申请，微信签发 | 会，有效期 5 年 | 所有请求签名失败，下单直接不通 |
| APIv3 密钥 | 你自己设定 | 不会自动过期，只在你主动重置时变 | 解不开回调内容 |

## 配置格式

`WECHAT_PLATFORM_PUBLIC_KEYS` 是一个映射，不是单个值：

```
序列号A=-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----\n;;序列号B=-----BEGIN PUBLIC KEY-----\n...
```

分隔符是两个分号。代码在 `src/lib/pay/wechat.ts` 的 `loadEnv()` 里解析成 Map，验签时按回调头里的序列号取对应的公钥。

这个设计就是为轮换服务的：加一个新条目不影响旧的，两边都能验。

## 轮换平台公钥的步骤

**第 1 步 提前拿到新公钥**

商户平台 → 账户中心 → API 安全 → 微信支付公钥。下载新的 PEM，记下公钥 ID。

**第 2 步 新旧一起配上**

不要替换，是追加：

```
WECHAT_PLATFORM_PUBLIC_KEYS=旧序列号=旧PEM;;新序列号=新PEM
```

**第 3 步 检查**

```bash
npm run check:pay-rotation -- --env-file ./deploy/prod.env
```

必须看到两个序列号都「可解析」，并且提示「具备轮换能力」。只有一个序列号时脚本会给出警告，那是刻意的。

**第 4 步 部署**

**第 5 步 观察至少一个完整的支付周期**

看日志里有没有「未配置 Wechatpay-Serial 对应的平台公钥」。有就说明还有第三个序列号在用，补上。

**第 6 步 确认旧的不再出现之后再删**

至少观察一周。删早了就等于没轮换。

## 轮换商户 API 证书的步骤

商户私钥换了，所有请求的签名都会变，所以这一步不能追加，只能切换。切换有短暂窗口，选在低峰期做。

1. 商户平台申请新的 API 证书，得到新的 `apiclient_key.pem` 和新的证书序列号。
2. **新旧证书在商户平台会共存一段时间**，这段时间里两个都能用于签名。
3. 更新 `WECHAT_MCH_SERIAL_NO` 和 `WECHAT_MCH_PRIVATE_KEY` 为新的一对。两个必须同时改，改一半会导致 `SIGN_ERROR`。
4. 跑 `npm run check:pay-rotation`，确认试签通过。
5. 部署，立刻做一次真实小额支付验证。
6. 确认无误后在商户平台作废旧证书。

## 轮换 APIv3 密钥

APIv3 密钥用于解密回调内容，微信侧不存在新旧共存。重置的瞬间，用旧密钥加密的回调就解不开了。

所以只在密钥可能泄露时才重置，重置流程是：

1. 选低峰期。
2. 商户平台重置 APIv3 密钥。
3. 立刻更新 `WECHAT_API_V3_KEY` 并部署。
4. 这中间到达的回调会解密失败，微信会重试，等新配置生效后重试会成功。
5. 部署后检查有没有停在 PENDING 的订单，对这些订单主动查单补状态。

## 定期检查

把这两件事放进季度日程：

- 跑一次 `npm run check:pay-rotation`，确认平台公钥不止一个序列号。
- 在商户平台看一眼商户 API 证书的到期日。剩余不足 90 天就安排轮换，别等到期。
